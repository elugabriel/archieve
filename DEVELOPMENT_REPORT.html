01 Overview

What was built

The archive is a multi-user web application for storing, organising, and retrieving theatre-lighting documentation — lighting plots, production photographs, gel and rig references, and cue paperwork. Each account gets private storage, a nested folder tree, search, and an AI assistant that generates reference images from a written description.

The codebase began as a general-purpose personal file store (internally still named clouddrive) and was adapted into a domain-specific archive for theatre lighting, then extended with the image-generation feature. The most recent phase — covered in detail below — wired in the Google Gemini image model, rebuilt the generation screen as a conversational interface, and raised the per-account storage allowance.

03 Architecture

How the pieces fit

The application is organised into four Python modules and a set of Jinja templates. Configuration is isolated so that secrets never live in source.

Modules

  • app.py — application factory, all API routes (folders, files, upload, download, thumbnail, search, storage, image generation), startup tasks.
  • auth.py — a Flask blueprint holding registration, login, and logout, with server-side validation and bcrypt hashing.
  • database.py — the SQLAlchemy models: User, Folder (a self-referential tree via parent_id), and File.
  • config.py — configuration object plus a minimal .env loader so credentials are read from the environment.

Data model

A User owns many Folder and File rows. Folders reference an optional parent, giving an arbitrarily deep tree. Every File records its owner, its containing folder, size, detected type, download count, and — for AI output — a source flag of generated and the exact prompt used, so generated assets remain traceable.

Storage and safety

Uploads are written to disk under a UUID-prefixed name to avoid collisions and path games; the original filename is preserved separately for display and download. Every file and folder route checks ownership before acting. Folder moves are guarded against creating a cycle, and folder deletion recurses through children, removing files from disk and reconciling each owner's storage counter.

05 Features

Implemented functionality

Accounts and sessions

Registration validates username uniqueness, email format, password length, and confirmation match on both client and server. Passwords are stored only as bcrypt hashes. Sessions are handled by Flask-Login with an optional persistent "remember me"; every application route outside the auth blueprint requires a logged-in user.

Folders and files

Users create nested folders, move them (with cycle protection), and delete them recursively. Uploads accept up to ten files per request within a 50 MB request ceiling, are checked against the account's remaining quota, and are stored under collision-proof names. Downloads stream the file under its original name and increment a per-file counter.

Thumbnails and search

Image uploads get a 200×200 thumbnail via Pillow, with a graceful fallback to the full image if generation fails. Search runs a case-insensitive substring match across both file names and folder names from a two-character minimum.

Storage quota

Each account carries a byte allowance (now 1 GB, set by USER_STORAGE_LIMIT and overridable per deployment). Usage is tracked incrementally on every upload, generation, and delete, and surfaced as a coloured progress bar that shifts from green to amber to red as it fills.

AI image generation

From the creation screen a user describes an image; the server calls the Gemini image model, extracts the returned image bytes, writes them to the archive as an owned File tagged generated with its prompt, and returns it to the interface. The generated image is a first-class archive object from the moment it exists — searchable, movable, downloadable, and counted against storage.

06 Focus

The Gemini image pipeline

The image feature was the phase with the most design decisions, spanning credential handling, an external API contract, and a new interface. Each is recorded below.

Credential handling

The API key must not enter source control. Rather than add a dependency, config.py gained a compact .env reader that loads key–value pairs into the process environment using setdefault, so a variable exported by the host always wins over the file. The key lives in .env; .env, the virtual environment, the database, and the upload directory are all excluded through .gitignore. If GEMINI_API_KEY is absent the client is simply not constructed and the feature reports itself as unconfigured instead of crashing.

Request and response

A generation request is a single generate_content call with the prompt as its only content. The response is a list of candidates, each holding content parts; the server walks these parts and takes the first with inline image data. Missing image data, an over-long prompt, and an exhausted quota are each handled as distinct outcomes with their own status code and message.

Error classification

The initial implementation returned the raw exception string, which meant a quota response arrived in the interface as an unreadable JSON blob. The handler now inspects the error: a 429 or RESOURCE_EXHAUSTED becomes a plain-language explanation with the parsed retry delay; a rejected key becomes a 401 pointing at .env; anything else becomes a generic upstream-failure message.

The creation screen

Generation was previously triggered by a native prompt() dialog. It is now a dedicated page modelled on a chat assistant: a conversation transcript of prompts and results, an auto-growing composer, example prompt cards, and a row of style modifiers that append to the description. Each result carries its own controls — download, open in the archive, and regenerate — and the interface degrades to an explanatory banner when the feature is unconfigured.

Finding — free tier

End-to-end testing surfaced a quota response with limit: 0 for the image model. Gemini's image generation has no free allowance; it requires billing to be enabled on the associated Google Cloud project. This is an account-provisioning step, not a code defect — the request authenticated and reached the API correctly. The error-handling path above was added so the condition is reported clearly rather than as a stack trace.

09 Status

Current state and known limitations

  • Image generation is provisioning-blocked. The code path is complete and verified; it will produce images once billing is enabled on the Google Cloud project for the key.
  • Development configuration. The app runs on the Flask debug server against SQLite. A production deployment would need a WSGI server, a stronger SECRET_KEY (now read from the environment), and a managed database.
  • Upload ceiling. Total storage is 1 GB per account, but a single upload request is still capped at 50 MB by MAX_CONTENT_LENGTH.
  • No automated test suite. Verification is currently manual and script-driven.
10 Next
